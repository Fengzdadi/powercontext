# 技术说明：端侧向量化 + seekdb 混合检索

**整体结构**：浏览器（Web Worker 中的 Transformers.js / ONNX Runtime Web）→ Node 服务（静态文件 + JSON API，seekdb-js）→ seekdb 1.4.0（Docker）。

- 文档和查询的向量只在浏览器里计算；
- 服务端只负责存储与检索，不做推理；
- 测量数据见第 5 节，原始数据与完整报告在 `bench/results/`。

## 1 模型与量化

**模型**

- 上游：[`intfloat/multilingual-e5-small`](https://huggingface.co/intfloat/multilingual-e5-small)@`614241f6`，MIT 许可。
  - 12 层，hidden 384，1.18 亿参数，XLM-R 分词器，词表 25 万。
  - 支持约 100 种语言，中英文检索效果好。
- 浏览器加载的是它的 ONNX 导出 [`Xenova/multilingual-e5-small`](https://huggingface.co/Xenova/multilingual-e5-small)，固定在 revision `761b726dd34fb83930e26aab4e9ac3899aa1fa78`。
- 用法遵循 E5 的约定：查询加前缀 `query: `，段落加前缀 `passage: `；mean pooling 后做 L2 归一化，按余弦距离比较。

**体积大头在词向量表**

- 250037×384 的词向量表占 9600 万参数，即模型的 82%。
- 因此只量化 Transformer 层的 MatMul 是不够的：词向量表（Gather）必须一起压缩。

**INT8 量化配方**：ONNX Runtime 动态量化。

- MatMul 权重 → INT8：对称、按张量、满量程（`MatMulInteger` + 运行时 `DynamicQuantizeLinear`）。
- 词向量 / 位置向量表 → UINT8。
- 两个激活×激活的 MatMul（QKᵀ、attn·V）保留 FP32。
- 不需要校准数据。

**FP16 配方**：全部权重和算子转为 FP16，图的输入输出保持 FP32。

**复现脚本**：`scripts/quantize.py`（`npm run quantize`）从 FP32 文件生成两个变体。

- 产物与 Xenova 预构建文件结构一致，体积相差不到 0.04%。
- 一个坑：新版 onnxconverter-common（1.16）会把内部 Cast 节点的输出标成 FP16，却不改该节点的 `to` 属性，ONNX Runtime 因此拒绝加载。脚本里修正了这一点。
- 应用默认加载固定 revision 的预构建文件；设置 `?source=local` 改为加载脚本产物。

**体积与压缩比**（`bench/results/model-size.json`、`quantize.json`）

| 变体 | ONNX 文件 | 压缩比 | 浏览器总下载 | 压缩比 | 与 FP32 输出的余弦（CPU，250 条） |
|---|---|---|---|---|---|
| FP32 | 470.3 MB | 1× | 487.4 MB | 1× | — |
| FP16 | 235.3 MB | ×2.00 | 252.4 MB | ×1.93 | > 0.99999 |
| INT8 | 118.1 MB | ×3.98 | 135.1 MB | ×3.61 | 平均 0.9899，最低 0.9800 |

- 浏览器总下载 = ONNX 文件 + `tokenizer.json` 等 3 个文件（17.1 MB，各精度相同）。它与加载测量记录的下载字节数一致。
- 脚本产物与预构建文件的输出逐条比较，余弦均为 1.0。
- 浏览器里实际算出的向量（90 条查询 + 128 段文本）与 WASM FP32 比较：FP16 平均余弦 ≥ 0.99999，INT8 平均 0.985（完整报告“输出保真度”一节）。

**检索质量变化**（下述评测集，K=10，纯向量检索；完整数据见第 5 节主表）

- FP16 与 FP32 几乎相同：WebGPU 上 nDCG@10 为 0.7675 → 0.7671，Recall@10 不变（0.985）。
- INT8：Recall@10 基本不变（0.985 → 0.982），nDCG@10 降 0.014（0.7675 → 0.7533），即相关段落仍在前 10，排序略有变化。混合检索的 nDCG@10 不受影响（0.6704 → 0.6715）。
- WASM 上 INT8 的收益主要是体积：速度与 FP32 / FP16 相当（第 5 节主表）。想要质量与 FP32 一致，可在设置里改用 FP16（252 MB）。

**评测集**：MIRACL v1.0 dev，固定种子抽取 60 条中文和 30 条英文查询。

- 语料是这些查询的全部标注段落，共 908 段，其中 706 段是人工标注的困难负例。
- 指标：Recall@10 / nDCG@10 / MRR@10，在文档级计算。
- mE5 微调时用过 MIRACL 的 train 划分；这里用的是 dev 划分。绝对分数可能偏高，但不影响量化前后的对比。

## 2 端侧运行

**后端选择**：Worker 先用 `navigator.gpu.requestAdapter()` 探测，再显式设定 `device` 与 `dtype`。

| 情况 | 后端 | 精度 |
|---|---|---|
| 有 GPU 适配器，且支持 `shader-f16` | `webgpu` | `fp16` |
| 有 GPU 适配器，不支持 `shader-f16` | `webgpu` | `fp32` |
| 探测失败，或 WebGPU 会话创建失败（驱动、显存、设备丢失） | `wasm` | `int8` |

- 降级时，徽标和横幅显示 WASM 以及具体原因，例如 `requestAdapter() 返回 null`。
- 用户也可以在设置或 URL 中强制指定后端和精度。
- **验证**：界面端到端测试（`bench/e2e.mjs`）在 Chrome 156 中各跑一遍。
  - GPU 可用时，自动选中 WebGPU · FP16（Apple Metal，shader-f16）。
  - `--disable-gpu` 时，`requestAdapter()` 返回 null，自动降级到 WASM · INT8 · 8 线程，徽标标注“自动降级”，横幅说明原因。
  - 两种环境下，导入、中英文检索、全文检索、两种融合、增量导入、跨知识库隔离和删除全部通过。

**WASM 多线程**

- 服务端发送 COOP/COEP 头，页面因此处于跨源隔离状态，可以使用 SharedArrayBuffer。
- 在此基础上启用 8 线程 SIMD。
- ORT 的 wasm 文件从本地 `node_modules` 提供，不依赖 CDN。

**模型加载与缓存**

- 模型文件同源提供，首次加载后进入 Cache Storage。
- 加载完成后立即做两次预热推理，把 WebGPU 管线编译和 WASM 内核初始化的开销挪到加载阶段，避免落在用户的第一次查询上。

**批处理**

- 分块：按句子贪心打包到不超过 300 token，相邻块重叠一句（不超过 40 token）。每块前加文档标题，向量和全文两路都能利用标题。
- 批次：先按长度排序再按 16 条一批，减少填充。批处理在 WebGPU 上收益明显；在 WASM 上批处理本身几乎没有收益，主要靠排序避免填充浪费（第 4 节）。
- 形状分桶（序列长度对齐到 16/32/…/512 档位）曾被设想用来在 WebGPU 上复用已编译的管线。批量导入实测反而更慢（第 4 节），所以默认关闭，只保留为可选项。单条查询在 WebGPU 上首轮有改善（15.3 → 8.4 ms），热中位数差别在噪声范围内（12.3 → 10.5 ms），见完整报告。
- 查询向量设 256 条 LRU 缓存。

## 3 seekdb 使用

**数据模型**：每个知识库是一个 seekdb-js collection，由 `createCollection` 创建。

- 表结构：`_id`、`document`、`embedding VECTOR(384)`、`metadata JSON`。
- 向量索引：HNSW，cosine，m=16，ef_construction=200，ef_search=100。
- 全文索引：IK 分词，smart 模式。
- 另有三张表：`kb_registry`（版本号与计数）、`kb_document`（内容哈希，驱动增量导入）、`kb_import`（批次状态与阶段耗时）。
- 知识库的全部状态都在 seekdb 中。

**混合检索**：每次查询只有一条 SQL：`SELECT DBMS_HYBRID_SEARCH.SEARCH(table, params)`。

- `params` 的组成：
  - `query.match`：全文路；
  - `knn {k: 50}`：向量路；
  - `rank.rrf {rank_window_size: 50, rank_constant: 60}`：融合；
  - `size`：返回条数；
  - `_source`：只取需要的列，加上两路各自的名次与得分。
- 加权求和模式用两路的 `boost`。
- 两路召回和融合都在 seekdb 内执行，界面上显示实际发出的参数，以及每条结果在两路中的名次。加权求和模式下 seekdb 不提供名次列（请求 `_keyword_rank` 会报 Unknown column），改为显示两路得分。
- 服务端会先去掉查询文本中的引号再发给 seekdb：`DBMS_HYBRID_SEARCH` 会把文本原样拼进它生成的 SQL，引号会导致语法错误（见 README“已知问题”）。

**导入协议**

1. **open**：按 `文档 key + 内容 SHA-256` 规划每篇文档是新增、变更还是未变。
2. **chunks**：带 `batch_id` 的多行 INSERT，每次 64 行；与下一批向量化并行进行。
3. **commit**：删除这些文档在已提交批次中的旧分块 → 登记文档 → 等待新分块可见 → 版本号 +1。
   - 另一个仍在进行中的导入写入的分块不会被删除。两个导入同时改同一篇文档时，最后提交的一方保留。
4. **abort**：按 `batch_id` 清理已写入的分块。服务启动时，遗留的未完成批次会被自动 abort。

**索引刷新**

- seekdb-js 建的 HNSW 索引是 `SYNC_MODE=ASYNC`：刚写入的行要等变更流追上之后，向量检索才能返回。
- 提交时用“探测”的方式等待：用最后写入分块自身的向量做 ANN 查询，直到返回它自己为止；超过 5 秒则改用显式的 `dbms_index_manager.refresh()`。
- 全文索引是同步的，不需要等待。
- 两种方式的实测对比见第 4 节。
- 也测了 `SYNC_MODE=IMMEDIATE`（512 行，与 ASYNC 交替 3 轮）：最后一行写入后立即可检索（3/3）；写入耗时 858 ms，ASYNC 为 1.03 s，这个规模下看不出写入代价。seekdb-js 的 `createCollection` 不提供该选项，应用沿用 ASYNC 加探测等待；改用 IMMEDIATE 需要自己写建表 DDL，留作后续改进。

## 4 状态与优化

**一致性**

- 提交与删除在服务端按知识库串行执行（互斥锁）。
- 每次导入或删除使版本号 +1。检索响应带回版本号，界面显示“结果来自 vN”。
- 界面用检索序号和知识库名丢弃过期响应：先发后到的结果，或切换知识库后才返回的结果，都不会被显示。
- 导入在分块全部可见之后才报告完成，所以“导入完成”之后立即检索，一定能查到新内容。端到端测试覆盖了这一点。
- `npm test` 直接对 seekdb 验证导入协议，覆盖跳过、替换、中止、两个并发导入同一篇新增或变更文档、删除。
- 局限：没有读隔离。分块在提交前就已写入表中，所以导入进行期间的检索可能提前看到部分新内容；提交负责替换旧版本、确认可见并增加版本号。

**优化与前后对比**（实测中位数，环境见第 5 节；每行只改变一个条件，完整对比见 `final__report.md` 的“优化前后对比（汇总）”）

| 优化 | 比较 | 前 → 后 |
|---|---|---|
| FP16（WebGPU 默认精度） | 导入 908 段的向量化吞吐 | 79.3 → 159.0 块/s（×2.0）；下载 487 → 252 MB；nDCG@10 −0.0004 |
| INT8（WASM 默认精度） | 浏览器总下载 | 487 → 135 MB（−72%）；吞吐 22.7 → 20.9 块/s（持平）；nDCG@10 −0.014 |
| WASM 多线程（COOP/COEP 跨源隔离） | INT8 批量向量化，1 → 8 线程 | 1.8 → 14.1 块/s |
| 批处理 + 按长度排序 | WebGPU FP16，批大小 1 → 16 | 73.2 → 128.2 块/s（+75%）；不排序为 102.6 |
| 按长度排序 | WASM INT8，批大小 16 | 10.4 → 14.1 块/s（+35%）；批处理本身无收益（批大小 1 为 14.2） |
| 形状分桶（未采用） | WebGPU FP16，批大小 16 | 120.3 → 88.2 块/s（−27%） |
| 加载阶段预热 | 用户的第一次推理 | 118 → 25 ms（WebGPU）；120 → 29 ms（WASM） |
| Cache Storage 缓存模型 | 再次加载 | 31.2 → 4.6 s（WebGPU FP16）；34.3 → 3.5 s（WASM INT8） |
| 向量化与写入流水线 | 908 篇的向量化 + 写入（交替各跑 3 次） | 11.2 → 7.6 s（−32%） |
| 跳过未改动文档 | 908 篇原样重导 | 8.9 s → 334 ms |
| 查询向量 LRU 缓存 | 重复查询的查询向量化 | 10.9 → 0.3 ms |
| 单次 SEARCH 调用 | seekdb 混合检索：SDK `hybridSearch()` → 一条 SQL | 16.1 → 9.3 ms |
| `_source` 只取所需列 | seekdb 混合检索 | 11.4 → 9.3 ms；响应 43.1 → 8.7 KB |
| 多行 INSERT | 写入，1 → 64 行/INSERT | 36 → 224 行/s |
| `add()` 代替 `upsert()` | 写入 64 行 | 882 → 130 ms |
| 探测等待代替显式刷新 | 64 行写入后到可被向量检索 | 609 → 69 ms |

- FP16 的收益在批量导入。单条短查询的向量化在 WebGPU 上没有变快（11.8 → 14.4 ms；同一模型的另一次运行为 10.0 ms），差别在噪声范围内。

## 5 测量

**条件**（完整环境表见 `bench/results/final__report.md`）

- **设备**：Apple M5 Pro（18 核，集成 GPU），48 GB 内存，macOS 26.4。
- **浏览器**：Google Chrome 156.0.8078.73，Playwright 驱动，headless。WebGPU 适配器为 apple / metal-3（支持 shader-f16）；无 GPU 环境用 `--disable-gpu`。
- **seekdb**：1.4.0 Docker 容器（`CPU_COUNT=4`、`MEMORY_LIMIT=4G`），索引与检索参数见第 3 节。
- **数据规模**：908 段 MIRACL 中英文段落，切成 994 块；90 条查询，每条重复 5 轮。
- **计时范围**：
  - 向量化吞吐：导入 908 段时端侧向量化的墙钟时间。批大小 16，按长度排序，与写入并行。
  - seekdb 检索：服务端执行一次 SEARCH 的耗时。
  - 端到端：从提交查询到结果渲染完成，包括查询向量化、HTTP、seekdb 和渲染。
  - 取去掉首轮后的中位数，首轮单独列出。
- **机器负载**：测量机器同时运行着其他任务，1 分钟 load average 在 46–355 之间（18 核）。CPU 密集的 WASM 数字受影响最大，绝对值偏保守。

**主表**（规范 3.2；90 条查询 × 5 轮，延迟为去掉首轮后的中位数，括号内为首轮；混合检索，查询缓存关闭）

| **WebGPU · FP16**（默认） | 252 MB（×1.93） | 159.0 块/s | 14.4 ms | 11.6 ms | 41.0 ms（42.5） | 0.985 / 0.767 | 0.942 / 0.670 |

| WASM · FP32（基线） | 487 MB（×1） | 22.7 块/s | 10.1 ms | 43.5 ms | 66.1 ms（71.9） | 0.985 / 0.767 | 0.942 / 0.670 |

**分阶段与首次 vs 热**（默认配置；导入 908 段，切成 994 块；模型加载为 3 次中位数）

| 阶段 | WebGPU · FP16 | WASM · INT8 |
|---|---|---|
| 模型加载：首次（空缓存）/ 再次（Cache Storage） | 31.2 s / 4.6 s | 34.3 s / 3.5 s |
| 推理：第一次（加载阶段预热）/ 之后单次 | 118 ms / 25 ms | 120 ms / 29 ms |
| 文档向量化 | 6.25 s | 47.5 s |
| 写入 seekdb（向量化结束后未被掩盖的部分） | 190 ms | 1.07 s |

| 导入后第一次检索 / 热中位数（seekdb 内） | 28.3 / 11.6 ms | 14.1 / 16.4 ms |
| 查询：向量化 / seekdb / 服务与网络 / 渲染 | 14.4 / 11.6 / 4.3 / 1.7 ms | 7.8 / 16.4 / 2.0 / 0.2 ms |

**怎么读这些数**

- **精度只影响向量化相关的列**。seekdb 检索在每一行做的是同样的工作（同一索引、同一批查询），各行之间 7.9–43.5 ms 的差异来自机器负载。seekdb 侧单独测量的中位数是 9.3 ms（p90 18.2 ms）。端到端随之波动：同一 FP16 模型的另一次运行（本地量化文件，输出余弦 1.0）得到 200.9 块/s、端到端 18.8 ms。
- **WASM · INT8 的提交 5.87 s** 中有 5.49 s 花在登记文档表的写入上。登记的是同样的 908 行，与推理配置无关；其他运行中这一步多为 70–484 ms（WebGPU · INT8 那次为 2.24 s），波动来自高负载下的 seekdb 写入。
- **首次 vs 热**：真正的首次开销在模型加载和第一次推理，分别由 Cache Storage 和加载阶段预热处理。查询首轮与热中位数的差别在噪声范围内（WASM · INT8 首轮反而更快）。
- **首次加载**的模型文件来自本机服务，不代表经公网下载的时间。经网络下载时，耗时大致与下载体积成正比：FP16 少下载 48%，INT8 少 72%。
- **INT8 在 WebGPU 上很慢**（16.6 块/s）：动态量化算子（`MatMulInteger`、`DynamicQuantizeLinear`）没有 WebGPU 实现，回退到 CPU 执行。所以自动选择从不把 WebGPU 和 INT8 组合在一起。
- **混合检索低于纯向量**（nDCG@10 0.670 vs 0.767）：语料是 MIRACL 的标注池，908 段中 706 段是与查询字面相近的困难负例；全文路单独的 nDCG@10 只有 0.544，主要把负例推高。加权求和（向量 0.7 / 全文 0.3）更低，为 0.574。混合检索仍是默认，因为任务要求库内混合检索，专有名词、编号这类字面匹配也需要全文路；界面可切换为纯向量。
- **原始数据**：`bench/results/final__*.json`，保留了每条查询每一轮的分阶段计时；每次运行的 Chrome 版本、GPU 适配器和机器负载记录在 `final__runs-*.json`。
